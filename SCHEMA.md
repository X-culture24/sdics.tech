# SDICS Database Schema

## Overview

PostgreSQL schema implementing the core SDICS system supporting ~1.8 million unregistered citizens across 10 counties. All tables include appropriate indexes for efficient querying.

## Table Structure

### 1. Officer (Registration Professionals)

```python
Field              Type              Constraints              Index
-------            ----              -----------              -----
id                 BIGSERIAL         PRIMARY KEY              -
national_id        VARCHAR(20)       UNIQUE, NOT NULL, ✓      YES (UNIQUE)
full_name          VARCHAR(255)      NOT NULL                 -
phone              VARCHAR(20)       NOT NULL, validated      -
role               VARCHAR(20)       NOT NULL, enum           YES
status             VARCHAR(20)       NOT NULL, default: ACTIVE YES
pin_hash           VARCHAR(255)      NOT NULL (bcrypt)        -
last_login         TIMESTAMP         NULL                     -
created_at         TIMESTAMP         auto_now_add             YES
updated_at         TIMESTAMP         auto_now                 -

Indexes:
  - national_id (UNIQUE)
  - status
  - role
```

**Constraints**:
- national_id must be 8 digits (Kenyan format)
- phone must be valid Kenyan format (+254... or 0...)
- pin_hash never stores plaintext PIN (bcrypt only)
- role: REGISTRATION_OFFICER, SUPERVISOR, ADMINISTRATOR
- status: ACTIVE, INACTIVE, SUSPENDED

**Key Properties**:
- National ID is primary identifier (not Django user)
- PIN stored hashed, generated by system during onboarding
- Tracks last_login for activity monitoring
- Status controls access (INACTIVE prevents login)

### 2. OfficerAssignedLocation (Jurisdiction Mapping)

```python
Field              Type              Constraints              Index
-------            ----              -----------              -----
id                 BIGSERIAL         PRIMARY KEY              -
officer_id         BIGINT            FK → Officer, CASCADE    YES
county             VARCHAR(100)      NULL                     YES
district           VARCHAR(100)      NULL                     YES
division           VARCHAR(100)      NULL                     -
location           VARCHAR(100)      NULL                     -
created_at         TIMESTAMP         auto_now_add             -

Constraints:
  - UNIQUE(officer_id, county, district, division, location)

Indexes:
  - (officer_id, district)
  - county
```

**Purpose**: Define geographical boundaries for each officer. Officers can only register citizens in assigned locations.

**Example**:
- Officer 1: Nairobi, Westlands, Kilimani, Karen
- Officer 2: Mombasa, Mombasa, Central

### 3. RefreshToken (JWT Token Revocation)

```python
Field              Type              Constraints              Index
-------            ----              -----------              -----
id                 BIGSERIAL         PRIMARY KEY              -
officer_id         BIGINT            FK → Officer, CASCADE    YES
token_hash         VARCHAR(255)      UNIQUE, NOT NULL         YES (UNIQUE)
expires_at         TIMESTAMP         NOT NULL                 YES
revoked            BOOLEAN           default: False           -
created_at         TIMESTAMP         auto_now_add             -

Indexes:
  - (officer_id, revoked)
  - expires_at
```

**Purpose**: Store refresh token hashes for invalidation on logout/deactivation.

**Behavior**:
- Created on successful login
- Marked revoked on logout or officer deactivation
- All tokens for officer invalidated on status change to INACTIVE
- Auto-cleanup via cron job for expired tokens

### 5. Citizen (Unregistered Citizens from Excel)

```python
Field              Type              Constraints              Index
-------            ----              -----------              -----
id                 BIGSERIAL         PRIMARY KEY              -
national_id        VARCHAR(20)       UNIQUE, NOT NULL         YES (UNIQUE)
full_name          VARCHAR(255)      NOT NULL                 YES
sex                VARCHAR(20)       default: UNKNOWN         -
date_of_birth      DATE              NULL                     -
tribe              VARCHAR(100)      NULL                     -
phone_number       VARCHAR(20)       NULL, validated          -
county             VARCHAR(100)      NOT NULL                 YES
district           VARCHAR(100)      NOT NULL                 YES
division           VARCHAR(100)      NOT NULL                 YES
location           VARCHAR(100)      NOT NULL                 YES
sub_location       VARCHAR(100)      NULL                     YES
village            VARCHAR(100)      NULL                     YES
registration_status VARCHAR(20)      default: UNREGISTERED    YES
registered_at      TIMESTAMP         NULL                     -
registered_by_id   BIGINT            FK → Officer, NULL       -
campaign_id        BIGINT            FK → Campaign, NULL      -
source_file        VARCHAR(255)      NULL                     -
created_at         TIMESTAMP         auto_now_add             YES
updated_at         TIMESTAMP         auto_now                 -

Indexes:
  - national_id (UNIQUE)
  - registration_status
  - (county, district)
  - (division, location)
  - created_at
  - full_name
```

**Excel Source Columns** (mapped automatically):
- Full Name → full_name
- Sex → sex (M/F/OTHER → MALE/FEMALE/OTHER)
- District → district
- Division → division
- Location → location
- Sub Location → sub_location
- Village → village
- ID Number → national_id (VARCHAR, preserves leading zeros)
- Date of Birth → date_of_birth
- Tribe → tribe
- Phone Numbers → phone_number

**Key Properties**:
- national_id is primary identifier (stored as TEXT to preserve leading zeros)
- Status: UNREGISTERED → REGISTERED (one-way)
- Records never deleted after registration, only status updated
- registered_by and registered_at track who registered and when
- source_file tracks origin Excel file
- county always populated (required for queries)

**Record Lifecycle**:
1. Created via Excel import with registration_status=UNREGISTERED
2. Officer searches and finds citizen
3. Officer registers citizen → registration_status=REGISTERED, registered_at=NOW(), registered_by=officer_id

## Batch Import Process

### Flow
1. **Scan**: Identify XLSX files in datasets/ folder
2. **Stream**: Load file row-by-row (no full load into memory)
3. **Detect Headers**: Fuzzy match Excel column names
4. **Parse Rows**: Normalize values, validate required fields
5. **Batch Accumulate**: Group rows (default 5000)
6. **Bulk Insert**: Transaction per batch
7. **Track Duplicates**: Skip national_ids already in database
8. **Log Results**: Update ImportLog with statistics
9. **Notify Admin**: Email with import summary

### Example: Import 1.8M Records

**File Structure**:
```
datasets/
  Nairobi/Gaps.xlsx      (500k rows)
  Mombasa/Gaps.xlsx      (400k rows)
  Kisumu/Gaps.xlsx       (350k rows)
  Nakuru/Gaps.xlsx       (200k rows)
  Kericho/Gaps.xlsx      (150k rows)
  (additional county files...)
```

**Execution**:
```bash
python manage.py import_citizens --batch-size 10000
```

**Processing**:
- ~1.8M records ÷ 10k batch = 180 batches
- Each batch: detect duplicates, validate, insert in transaction
- Total time: ~15-30 minutes depending on hardware
- Memory: ~500MB (streaming, not loading all)

**Results**:
```
ImportLog entries created:
  - 1 per file (Nairobi, Mombasa, etc.)
  - Cumulative counts in admin
```

## Performance Characteristics

### Indexes

**Citizen Table** (largest, ~1.8M rows):
- `national_id`: UNIQUE, enables registration lookup in O(1)
- `registration_status`: Fast filtering (UNREGISTERED vs REGISTERED)
- `(county, district)`: Hierarchical location queries
- `(division, location)`: Officer jurisdiction filtering
- `created_at`: Sort by insertion order
- `full_name`: Support name-based search

**Query Performance** (with indexes):
- Search by national_id: < 1ms
- Filter by county + district: < 10ms (25-record page)
- Search by full_name (partial): < 50ms
- Count by registration_status: < 100ms

### Estimated Size

```
Citizen table (1.8M rows × ~250 bytes/row) ≈ 450 GB
  Including indexes ≈ 600 GB total

Officer table (1k rows) ≈ 1 MB
Campaign table (100 rows) ≈ 50 KB
Registration table (varies with progress) ≈ scales with registrations
AuditLog table (all actions) ≈ scales with activity
```

## Constraints and Validation

### Database-Level
- UNIQUE(national_id) on Citizen and Officer
- UNIQUE(officer_id, county, district, division, location) on OfficerAssignedLocation
- Foreign key constraints with CASCADE on deletion
- NOT NULL on required fields

### Application-Level
- national_id: 8 digits (regex)
- phone_number: Kenyan format (+254... or 0...)
- sex: MALE, FEMALE, OTHER, UNKNOWN
- registration_status: UNREGISTERED, REGISTERED
- officer.role: REGISTRATION_OFFICER, SUPERVISOR, ADMINISTRATOR
- officer.status: ACTIVE, INACTIVE, SUSPENDED
- campaign.status: PLANNED, ACTIVE, CLOSED

### Business Logic
- AuditLog is append-only (no updates/deletes)
- Citizen records never deleted, only status changed
- Officer PIN never stored plaintext (bcrypt only)
- Refresh tokens revoked on logout/deactivation
- No concurrent registrations of same citizen (database locking)

## Backup and Recovery

### Backup Strategy
- Daily full backups of PostgreSQL
- Point-in-time recovery capability (WAL archiving)
- Test restore monthly

### Recovery Scenarios
- **Lost citizen record**: Restore from backup (AuditLog shows what happened)
- **Corrupted import**: Re-run import (duplicates skipped automatically)
- **Officer deactivated**: Restore from backup or manual re-activation
